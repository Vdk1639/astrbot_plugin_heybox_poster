# 事件按用户聚合与风险处置 · 正式任务单

- 编制日期：2026-11-01（北京时间）
- 核对基线：本地 `astrbot_plugin_heybox_poster` v0.7.1，提交 `7172bc3`
- 建议实施顺序：第二阶段；可先交付聚合查询，再交付风险处置。正式版本号由实际发布安排确定
- 前置任务：[通知回复防刷与评论发送限额](reply_ratelimit_正式任务单.md)
- 本单描述待开发行为；风险阈值为本项目启发式配置，不代表对某个用户“恶意”的事实认定。

## 1. 目标与范围

让管理员能够按用户查看事件、追踪重复触发和风险来源、人工封禁或解除，并在显式开启时按风险分自动过滤。不能为了风险识别增加一次可被攻击者滥用的模型调用，也不能改变原有审核、权限和发送未知保护。

交付拆成两个可独立验收的步骤：

1. **A：事件按用户聚合**。保留原平铺 API，增加档案维度、聚合、下钻及基础统计，不依赖风险模型已完成。
2. **B：风险记录和处置**。本地确定性规则、幂等记分、人工封禁/解除/调分、默认只观察、可选自动过滤、审核批准前复查。

不实现设备指纹、跨 UID 身份识别、LLM 风险裁判、规则 DSL、任意用户正则、自动重放过滤事件或对外发送管理员通知。

## 3. A 阶段：事件按用户聚合

### 3.1 查询契约

扩展既有路由 `/astrbot_plugin_heybox_poster/events`：

```text
GET /events?group_by=uid&profile_id=default&uid=&status=&post_id=&keyword=&start_time=&end_time=&page=1&page_size=30
```

- `group_by` 缺省/空字符串：保留现有平铺行为与返回字段；`uid`：用户聚合；其他值返回 400。
- `profile_id` 可选；传入时校验格式。读取允许当前配置档案或库中有历史事件的档案；两者均不存在返回 400。删除配置后的历史档案仅供查看，风险写操作仍要求当前配置档案存在。平铺、聚合和下钻全部支持同一个档案过滤。
- 未指定档案时按 `(profile_id, sender_uid)` 分组，不跨档案合并风险分。用户组必须返回 `profile_id`。
- 所有过滤先作用于事件，再对匹配事件分组。状态统计、事件数和帖子数均是**当前筛选结果内**的统计，不与全部历史混用。
- 风险字段是该档案/UID 的**当前快照**，不受事件时间/状态筛选裁剪；不能把筛选结果的累计分当当前分数。
- `total` 是组数，分页先分组后分页；按 `last_event_at DESC, profile_id, sender_uid, 匿名 event_id` 稳定排序。该排序解决同时间并列，不承诺数据实时变化时跨页快照一致。
- `page_size` 沿用现有 1–100 归一化，`page` 小于 1 沿用现有处理。空结果、越界页返回 200 和空 items；非法 group_by/时间参数返回 400。不能把正常空列表当异常。
- 时间过滤保持现有 `COALESCE(completed_at, updated_at, discovered_at)` 语义，`last_event_at` 取其组内最大值；`last_discovered_at` 另取组内 `MAX(discovered_at)`。时间均为 Unix 秒；空字符串沿用现有未指定语义，其他输入校验有限数值、start≤end，避免混淆“评论新到达”和“旧事件刚审批”。
- API 未传时间时保持原有不限范围；页面初次切入聚合时**显式设置并显示最近 7 天**。用户可以调整，不能服务端静默加隐藏时间条件。

建议返回（仍放在现有 `json_response` 数据封装内）：

```json
{
  "group_by": "uid",
  "page": 1,
  "page_size": 30,
  "total": 42,
  "items": [
    {
      "profile_id": "default",
      "sender_uid": "59051863",
      "sender_nickname": "最近昵称",
      "identity_verified": true,
      "event_count": 12,
      "post_count": 3,
      "last_event_at": 1793519670.8,
      "last_discovered_at": 1793519600.0,
      "status_counts": {"sent": 9, "ignored": 2, "dead_letter": 1},
      "event_type_counts": {"mention": 8, "reply": 3, "proactive_feed": 1},
      "risk_score": 35,
      "risk_level": "watch",
      "manual_blocked": false,
      "auto_filtered": false
    }
  ]
}
```

A 阶段未接入风险时，风险字段可返回空值或不返回，前端显示“未启用/未接入”，不要伪造为已评估的 0 分。

### 3.2 昵称、空 UID 与主动事件

- 昵称取筛选结果内按 `discovered_at DESC, id DESC` 最新事件的昵称（允许为空）；不能用 `MAX(sender_nickname)` 或审批更新时间冒充最新昵称。
- `identity_verified` 仅沿用 `Notification.sender_uid_verified` 的“平台提供非空 UID”语义，不表示实名验证；空白 UID 及本地兜底锚点不构成可封禁身份。
- 不把所有空 UID 合成“一个用户”。保留每条未验证事件为独立匿名组，`identity_verified=false`，返回可下钻的 `event_id`，显示“UID 未提供”。平铺查询补可选正整数 `event_id`，与其他过滤条件取交集，非法值返回 400；每条匿名事件计入一个组，排序/计数/分布查询均保留 event_id，不能在第二次批量查询时又按空 UID 合并。
- 已验证组下钻必须同时携带 `profile_id + uid` 和当前时间/状态等筛选条件；保留返回聚合视图时的筛选和页码。
- `proactive_feed` 的 `sender_uid` 是帖子作者，属于主动浏览来源而非该用户主动触发。聚合可展示这类事件，但要显示类型分布/主动来源标记；风险行为计数只使用 `mention/reply`。

### 3.3 查询实现与面板

- 复用当前过滤构造，可提取一个小型私有函数；不引入查询框架。
- 先取得本页用户组，再一次批量查询该页状态分布/风险快照；禁止每用户额外查一次数据库的 N+1。
- `status_counts` 使用完整 `EventState` 值；可只返回非零项，前端将缺省项显示 0。`generated` 表示生成完成，不等于审核库的 `pending`；不伪造不存在的事件状态。
- 在 `index.html` 事件区增加“按事件/按用户”切换和档案筛选，`app.js` 复用 `bridge.apiGet`、`nextRequest/currentRequest` 与安全文本 DOM。
- 切换筛选/模式重置到第 1 页；聚合条数文案用“组/用户记录”。显示档案、UID/匿名、最新昵称、事件/帖子数、状态/类型分布、最近时间、风险状态和下钻操作。
- 匿名组禁用 UID 封禁/调分。用明确文字说明不能可靠归属，不能凭昵称推断身份。
- 页面卸载/切档案后迟到响应不能写回，新详情请求复用现有版本检查；操作按钮具备忙碌态和键盘可访问性。

## 4. B 阶段：风险与处置语义

### 4.1 范围、分数和实际拦截分开

风险档案按 `(profile_id, sender_uid)` 隔离，UID 必须是真实提供的发送者 UID。不同档案风险不自动共享，与前置任务按发送账号共享的额度是两个不同维度。

- 分数 `0..1000`，初始 0；等级由有效分数和当前阈值计算：`normal <20`、`watch 20..59`、`blocked >=60`。
- 不把 `level/auto_blocked/score` 三份可推导状态持久化后各自更新。建议只存分数和人工封禁，等级、是否达到阈值、是否真正自动过滤在读取时推导。
- `auto_filtered = risk.enabled && risk.auto_filter_enabled && score >= auto_filter_score && !owner_exempt`。
- `manual_blocked` 独立于风险总开关，人工封禁立即生效；不改写现有 `permissions.user_blacklist`，避免解除后名单漂移。
- 已验证主人在 owner_exempt 开启时不计分、不自动过滤；**人工封禁和原有硬黑名单仍生效**。普通白名单不会绕过人工封禁/自动过滤。
- 关闭风险评分不关闭人工封禁；关闭自动过滤仍可计分、观察。界面明确显示“已达阈值，自动过滤未开启”，不能简单显示“已封禁”。

### 4.2 默认模式及配置

新增 `risk` 分组，字段保持平面，适配现有 schema 表单，不加入 `risk.rules.<id>` 任意嵌套配置：

| 配置键 | 默认 | 范围/语义 |
|---|---|---|
| `enabled` | true | 是否评估并累积新风险 |
| `auto_filter_enabled` | false | 达阈值是否自动过滤，默认只观察 |
| `watch_score` | 20 | 整数 1–999 |
| `auto_filter_score` | 60 | 整数 2–1000，必须大于 watch_score |
| `flood_window_minutes` | 10 | 整数 1–1440 |
| `flood_threshold` | 8 | 整数 2–1000，含当前事件 |
| `burst_score` | 20 | 整数 0–1000，0 关闭该规则 |
| `repeat_score` | 15 | 整数 0–1000，0 关闭该规则 |
| `injection_score` | 25 | 整数 0–1000，0 关闭该规则 |
| `privacy_score` | 30 | 整数 0–1000，0 关闭该规则 |
| `owner_exempt` | true | 已验证主人免自动评分/过滤 |

本期不实现自动衰减与单独“关键词黑名单加分”：前者引入时间结算和封禁到期语义，后者会把用户明确的硬过滤政策误解为恶意判断。初版保留手动清分和完整审计即可；需要衰减时另立规则和测试，不做一个实际未生效的配置项。

`DEFAULT_CONFIG`、严格类型校验、`_conf_schema.json`、README、配置 API/页面默认值同步，旧配置通过现有合并机制补默认。设置保存走现有安全重载，无需新增后台评分定时器。

## 5. 初版规则与误伤控制

规则在代码中固定、版本化，无额外网络调用。不提供任意正则输入；文本扫描长度有上限，模式不能出现灾难性回溯。规则解释必须可在单元测试中重复得到。

建议规范化使用标准库 Unicode NFKC、casefold 和连续空白折叠，取通知正文前 4000 字，记录规范化版本；空文本不计算重复内容。由此得到 SHA-256 用于重复判定，不复用机器人输出 hash，也不复用会删除重复行/改变正文的上下文清洗结果。规则只承诺检查这一有限输入范围，不能把截断后的“未命中”当作整条内容安全。

| 规则 | 判定 | 默认分 | 累加限制 |
|---|---|---:|---|
| `flood_burst` | 同 UID 在窗口内独立入库的 mention/reply 数达到 flood_threshold | 20 | 一个滚动 flood_window 内每 UID 只加一次 |
| `flood_repeat` | 同 UID 在该窗口内最近 3 条独立入库通知的规范化正文相同且非空 | 15 | 相同内容 hash 在一个窗口内只加一次 |
| `inject_override` | 明确要求忽略/覆盖既有指令、伪装系统/开发者权限 | 25 | 同一事件注入类别最多加一次；相同规范化内容在窗口内不重复加 |
| `privacy_exfiltration` | 明确要求提供机器人的密钥/凭据/非公开主人信息等，要求“索取动作 + 受保护对象”组合 | 30 | 同一事件隐私类别最多加一次；同上内容去重 |

不采用草案里的以下宽泛触发：单独出现“系统提示/system prompt”“你现在是”“调用工具”“把…发给我”“cookie/token”“配置/数据库/日志/后台”。这些词可用于正常技术交流或角色互动，不能直接认定为攻击。

文本规则必须包含中文/英文正例与正常讨论、引用、否定例；对于无法低成本区分的引用/歧义，保守不加分或仅记观察标签。正则只能识别已定义的启发式模式，不能声称完整识别提示词注入。先通过观察数据评审误报，再显式开启自动过滤。

首版不做 `flood_multi_post`：正常用户在多个帖子互动并不必然异常，账号/用户预算已处理成本问题。也不因单次命中额度上限、关键词黑名单而自动加分。后续有真实攻击样本再补独立规则及误伤测试。

行为计数按 `(profile_id, sender_uid)` 隔离。对当前事件 e，令 `t=e.discovered_at`、`W=flood_window_minutes*60`，只统计 `(t-W, t]` 内已独立入库且有行为资格的 mention/reply，含当前事件；同发现时间以 `id <= e.id` 截止，不读取当前事件之后发现的通知。最近三条按 `discovered_at DESC, id DESC` 取得，不能只查已评分/已回复或与当前 hash 相同的三条。这样积压、重试和并发处理不会把“处理时刻”当成到达时刻；去重通知不新增窗口计数。

历史回填不等于短时刷屏。首次入库时固化来源时间有效性/明确回填标记：只有非回填且来源时间为有限正数、落在 `[discovered_at-W, discovered_at]` 的通知参与 flood/repeat 的计数和加分；资格按首次入库的 W 固化，恰好早一个窗口仍允许，超过才排除。时间缺失、异常或未来时间保守排除行为规则，文本规则仍可评估。当前解析器会把缺时间默认成 observed_at，恢复也会回退，不能用这个兜底值冒充已提供有效来源时间；须保留来源有效标志，历史无标志事件不推定合格。界面说明“历史回填/时间不明，未计短时风险”。

四条规则的滚动去重冷却以事务内服务端当前时间和该去重键上次实际登记的审计时间判断：距上次不足 W 不再加分，恰好 W 可再次加分；它与上述到达计数窗口分开。burst 键为档案/UID/规则，其他规则再含正文 hash；规则版本仅供解释，不得令重载规则、人工清分或重试绕过去重。超过 4000 字的原始正文不参与 repeat、注入及隐私规则加分（burst 仍适用），避免把相同前缀、不同后文误当重复攻击；可保留前 4000 字的命中观察标签。

只对当前通知发送者自己写的内容加文本风险分；原帖、同楼层他人的评论、历史上下文和图片转述中的攻击文案不能记到当前发送者头上。图片/OCR 注入依靠现有不可信边界，本期不声称可自动归责识别。

## 6. 数据模型与幂等事务

推荐只新增两张表及事件评估标记，接入 `xiaoheihe.db` 现有迁移：

**`user_risk` 快照**：`profile_id + sender_uid` 主键；`score`、`manual_blocked`、`note`、`last_hit_at`、`created_at`、`updated_at`。没有命中且没有人工操作的用户不必创建空档案。

**`user_risk_events` 审计**：主键、profile、sender_uid、可空 incoming_event_id、rule、delta、before_score、after_score、去重用 rule_key、规则版本、details、created_at、可空 operator。规则记录、block/unblock/reset/adjust 都在同一审计表；无事件的管理操作使用独立操作 ID，不能被 event_id 唯一约束意外合并。

**`incoming_events` 新标记**：可空 `risk_evaluated_at`，以及定义清楚的 `risk_delta`（本事件实际加分）、`risk_score_after`（评估后的快照）、可选命中代码列表。历史未评估为 NULL，不以默认 0 假装已评估。只有审计表不能表示“已评估但零命中”，所以必须有事件级完成标记；另以最小状态/原因区分已评估、永久跳过与待评估，不能让禁用时跳过和旧库 NULL 混为待重试。行为资格、首次规范化 hash 需能在窗口查询时稳定取得，不因重试、正文清理或配置重载重新解释。

数据库保证：

- `(incoming_event_id, rule)` 的自动规则记录幂等（自动记录必须有关联事件，不能依赖 SQLite 对 NULL 的唯一性）；同规则滚动窗口/内容去重也在事务内检查和登记，两个并发事件不能同时拿到一次加分。封顶后实际 delta 为 0 的命中也登记去重，审计 delta 和事件 risk_delta 记录裁剪后的实际变化。
- 单个 `BEGIN IMMEDIATE` 中检查事件是否已评估、读取窗口/最新分数、计算命中、更新快照/审计/事件标记。事务内不做网络/模型调用，避免锁重入。
- 幂等跳过评分只表示不再加分；每次处理和审批仍读取当前人工封禁、分数、阈值及开关，不能用事件首次评估的旧快照决定今天是否放行。
- 本事件累计后达到阈值时，当前事件即按有效模式过滤，不必等下一条。
- 重新轮询、任务恢复、自动重试、编辑同一评论导致同外部评论 ID 重复出现，都不重复评分。改规则/开关不自动补评历史事件。
- 对无 UID、本人消息、主动浏览或禁用模式写永久跳过原因，不建立假 UID 档案。禁用期间首次入库即固化跳过，启用前已入库的积压/迁移历史不补评；重载开关不能让它们恢复为新事件。评估因数据库异常未提交的事件仍待重试，不能标为永久跳过。

在 `repository.py` 增加原子评估/快照查询/分页审计/管理更新方法。可新增一个小型 `risk_service.py` 放固定文本规则和处理决策，持久化与原子性仍由 Repository 负责；不把纯 `PermissionService` 改为会扣分的 IO 服务。

## 7. 接入点与审核联动

通知链路：

```text
claim_event / claim_retry_event
→ 现有自身消息保护（包括可信发送者 UID 与当前账号 UID 相等的判断，须在评分前执行）
→ 按事件幂等风险评估 + 人工封禁/有效自动过滤
→ PermissionService.decide()
→ 第一阶段原子回复准入
→ context_builder.build()
→ AstrBot / 图片理解 / 压缩
→ 统一发布审核
```

评估在 `_handle()`，不要在 `enqueue()` 的优先级查询或 `adapter._dispatch()` 中再评一次。对因待处理队列满而延后的事件，评分可以等实际处理；防刷的成本上限仍由第一阶段控制。短时计数从已入库事件读取，不只看已回复事件。

风控过滤使用 `ignored`、`should_filter=True`，错误分别写“用户已被人工封禁”或“用户风险分达到自动过滤阈值”，固定 reason 分别为 `risk_manual_blocked`、`risk_auto_filtered`；审核来源无法解析用 `risk_source_unresolved`，读库异常不能冒充这些策略命中。日志及返回行为说明是否为硬名单/人工/自动/频率限制。不得回复一条“你已被封禁”到评论区，避免额外消耗和对抗。

**审核必须复查**：通知生成后再封禁该 UID，旧待审回复不能在批准时绕过。`PublishingService.approve()` 从 `review_events` 读取该审核的全部 notification 来源（兼容旧审核主来源），逐一校验可信事件的 `profile_id + sender_uid` 和当前风险状态；不能只取 `payload._delivery.event_id` 或第一条来源。任一通知来源被有效封禁就阻止整个审核项发送，不拆出新回复。明确无 UID 的来源不推断身份，仍按第一阶段匿名限额处理；缺关联/无法确认是否为通知来源与“已确认无 UID”不同，不能静默当成手动来源放行。

优先读取保留事件行的身份列：`prune_event_bodies()` 只清 `content/raw_json`，不会删除 `sender_uid`。待审关联事件应保留最小行/完整来源关系；只有原关联无法保留、整行即将删除时，才在程序控制的审核来源关联中保存最小 `profile_id/event_id/UID及提供标志`。旧审核可从可信关联回填；原事件已删除且无可信快照、来源映射不完整/冲突时保守拒绝真实发送并提示人工核查，不能从昵称、正文或当前登录账号重建对端 UID。风险快照无需复制正文或凭据。

批准前和实际发送闸前复查当前状态；新增 await 后重新校验绑定账号/模拟开关，任一来源校验不能绕开第一阶段原子发送闸。以进入持久化发送尝试前的最后检查为策略生效边界，已开始或未知的网络发送不能宣称可撤回；无法跨两库事务保证绝对同时封禁/发送原子性。策略拒绝仍 pending 的机器可读结果、特定本地拒绝异常/领取释放和 `pages/account/publishing.js` 展示统一复用前置任务单第 5.2、5.3 节契约，不另定义状态；不得被现有通用异常处理改成 failed/send_unknown。解除后可重新审阅仍 pending 的内容，已 ignored 的通知不自动恢复。

主动浏览不算“对作者的通知回复”，因此不自动把作者风险分当作通知封禁。继续用已有作者黑名单过滤主动来源；后台手动指定目标评论也不从外部正文推断目标 UID。所有这些来源仍受第一阶段发送额度和已有工具权限保护。

**故障策略**：读库/事务失败则停止该事件的模型处理，写脱敏运行错误，走现有有上限的重试；不凭空加分、忽略用户或放行未知封禁状态。新增评估必须纳入 `_handle()` 的重试保护区，不能放在当前仅包围上下文/分发的 try 之外后只依赖 worker 日志捕获。异常不可退出整个轮询器。风控后台接口失败返回明确错误且不产生部分更新。

## 8. 管理 API 与人工操作

所有接口沿用 `WebApiController._unauthorized()` 的 Dashboard 会话鉴权，前缀不变。建议使用固定路由与 query/body 参数，便于严格验证：

| 路由 | 方法 | 内容 |
|---|---|---|
| `risk/users` | GET | 按 profile/uid/level/manual_blocked、分页列风险档案 |
| `risk/users/detail` | GET | 指定 profile+uid，返回快照、分页审计及事件查询入口 |
| `risk/users/block` | POST | 人工封禁，confirm:true + note |
| `risk/users/unblock` | POST | 解除人工封禁，可选 reset_score:true |
| `risk/users/adjust` | POST | delta + note，调整风险分 |

返回状态：匿名会话 401；非法参数/非布尔 confirm 400；未知档案 400；仅历史档案 GET 可读、写操作 400。无风险记录的合法 UID 详情返回正常的“无记录”结构。GET 无副作用，空结果/超页仍为 200；level 仅 normal/watch/blocked，排序仅服务端固定白名单，沿用 1–100 分页上限。

人工操作约束：

- profile 必须存在，sender_uid 必须是平台 UID 的合法格式（按现有真实样本固定，不能把本地锚点当 UID）；note 最多 200 字并严格验证类型。
- 所有变更要求 JSON 布尔值 `confirm:true`；delta 是非 bool 整数，范围 -1000..1000，有效分数裁剪到 0..1000，审计保存实际增减和前后值。
- 用已认证 `request.username` 记录操作者，不接受客户端自报管理员名。审计详情/备注按现有脱敏函数处理。
- block/unblock 重复请求幂等：无实际变化不重复插入状态变更审计。adjust 由前端禁用重复提交，API 文档说明非幂等；如需自动网络重试，必须先加操作请求 ID 去重。
- 默认 unblock 只撤人工封禁，分数保留；若自动过滤仍生效，返回/显示“人工封禁已解除，但风险阈值仍阻止处理”。reset_score 明确归零并写审计，自动过滤由归零后的分数推导。
- 清分不删除审计，不删除既有权限黑名单；解除后仍可能被原有硬名单或第一阶段限额拦截，界面必须显示当前实际原因。
- 返回值沿用现有响应封装，禁止原始异常/SQL/凭据泄漏。

## 9. 面板与数据安全

聚合行进入同页用户详情面板即可，不新建路由系统。显示当前分数/等级、评分与自动过滤开关、人工封禁、最近事件、命中规则、实际增分、前后值、时间和人工操作。

- “查看事件/风险记录/封禁/解除/调分”复用现有 bridge、确认弹窗、忙碌态、请求版本检查；写操作完成后刷新当前用户与列表。
- 确认弹窗明确档案、UID、备注、是否清分；缺 UID 禁止操作。等级/封禁状态用文字加颜色，不能只靠颜色表达。
- 动态内容使用文本节点，禁止不可信 HTML；详情分页，不一次加载全部审计。
- 规则详情不保存命中的正文切片，尤其不能把 80 字未脱敏内容复制进日志/审计。默认保存规则 ID、窗口计数、不可逆内容 hash（如需）、规则版本。
- 常见 hash 不等于匿名化；只在实现去重所需时保存，权限与保留期同审计。操作备注、错误和诊断统一脱敏后限长，先脱敏再截断。
- 不新增邮件/私信/群消息通知；告警先复用 Runtime 状态页 `_alerts` 与结构化日志，仅在实际过滤状态变化时产生，不能每条 blocked 事件重复弹告警。

新增风险分不提高 Agent 权限。核查 `main.py` 的管理员/allowed_users 以及上下文、图片工具钩子，确保社区文本不能改身份或调用敏感写工具；保持 `sanitize_reply_text/redact_text`。正则评分不是安全边界，也不承诺隐藏管理员主动通过其他插件暴露给模型的数据。

## 10. 升级、存储与实现顺序

1. 先完成第一阶段的准入原因/事件身份约定，或仅交付 A 聚合。
2. 统一事件过滤构造，增加 profile、可选 event_id、分组总数、稳定昵称/排序，完成 A 页面回归。
3. 追加 `MIGRATIONS`/`MIGRATION_MARKERS`，新增快照、审计、事件评估标记。实施时使用当时下一迁移号，旧迁移不动。
4. 实现少量固定规则、原子幂等评估，接入通知处理和审批前复查。
5. 实现鉴权管理 API、审计和同页风险详情，接配置动态 schema。
6. 扩展清理预览、实际清理、表计数、诊断及软上限策略。默认审计保留沿用 `retention.dedup_days`，不再新增一组保留配置。

有效人工封禁和非零风险快照不能因事件正文清理而消失；风险审计不级联删除档案快照。旧事件删除后可将审计 event 引用置空，必须在迁移时选择可行 FK/清理顺序；待审关联身份按第 7 节保留或在删除前保存最小可信快照。审计可按保留期清理，“操作时只追加”不等于永久无限增长；保留期/软上限清理均不得删除尚在行为/去重窗口内的资格、hash 和审计，也不能让仍在窗口内的规则重新加分。

历史事件不自动回评、不自动产生封禁。现有 `idx_incoming_sender` 足以服务基础行为窗口，评分审计增加按 profile+uid+time/rule 的必要索引。聚合查询使用真实查询计划和批量读取验证，不能只写一个 LIMIT 就声称不会扫描大表；无需引入物化汇总表，除非测试发现现有索引不可接受。

版本文档只在 dev 变更中记录已实现能力和默认观察模式；未实机通过不合并 main、不发布正式 Release。保持 VERSION、metadata 等版本文件符合实际发布流程。

## 11. 验收清单

### A：聚合与兼容

- [ ] 缺省 group_by 的旧调用/字段/无时间范围语义保持；旧页面默认按事件。

- [ ] status/keyword/post/time 在分组前生效，total 是组数，分布合计等于 event_count，帖子数正确。
- [ ] 空 UID 不混成一个真实用户，可单事件下钻，操作入口禁用；主动浏览显示来源且不计行为风险。

- [ ] 到达窗口开闭边界/同时间 ID、跨档案隔离、积压乱序、连续最近三条（中间不同正文会打断）、冷却恰好 W、长正文相同前缀均有固定预期；明确回填、时间缺失/异常/未来及旧库无标志不被当短时洪泛。
- [ ] 每事件/每规则幂等，零命中也不重评；并发窗口只加一次；重试/重启/重复通知不叠加。
- [ ] 事务中快照/审计/事件标记同时成功或回滚；分数上下限、实际增减和操作者正确。
- [ ] 当前事件加分跨阈值立即生效；观察模式达到阈值仍处理，明确开启自动过滤才 ignored，且无任何模型调用。
- [ ] owner 可信 UID 豁免；昵称/正文冒充无效；硬名单和人工封禁仍优先；未知 UID 不建立档案。

- [ ] 通知生成后封禁、审批时策略变更/换号/模拟开关变化，旧待审不能绕过；本地拒绝 pending，未知发送不变回 pending。

- [ ] 全风险路由未登录 401；confirm 缺失/字符串 true、非法 UID/profile/delta/note 无副作用。
- [ ] 封禁/解除重复请求幂等；调分不自动重试；跨档案不串数据；返回字段无凭据。
- [ ] 数据库/规则异常不放行未知封禁状态、不凭空惩罚用户、不终止轮询器。

## 12. 完成条件与风险

交付代码、迁移、所有入口联动、配置/API/页面/README、dev 变更和离线测试结果；A/B 分步交付时明确哪个已完成。真实验收另行记录，不把任务单里的勾选框当作测试通过证据。
