# 通知回复防刷与评论发送限额 · 正式任务单

- 编制日期：2026-11-01（北京时间）
- 核对基线：本地 `astrbot_plugin_heybox_poster` v0.7.1，提交 `7172bc3`
- 建议实施顺序：第一阶段；版本号由实际发布安排确定，不在任务单编制时修改版本文件
- 关联任务：[事件按用户聚合与风险处置](event_group_and_risk_正式任务单.md)
- 本单是开发与验收规格，所列新增接口、表和配置均为待实现内容；不代表线上已具备。

## 1. 目标与范围

打开 `reply.reply_to_direct_replies` 后，不同评论可以持续触发机器人。需要同时限制模型处理量和账号实际评论量，并保证审核等待、并发、重试、换号和重启不会绕过限制。

本期完成：

1. 同一根评论楼层默认只接受一次自动回复任务，包括正在生成、待审核、已发送和发送未知的任务。
2. 已验证用户每日最多进入 5 次通知回复处理；单个小黑盒发送账号每日最多进入 30 次通知回复处理。
3. 同一小黑盒发送账号每日最多真实发送 30 条评论，通知、主动浏览、手动评论共用这一上限。
4. 被拒绝的事件持久化为 `ignored`，保留原因，且在构建上下文和进入模型之前停止。
5. 复用统一发布审核和现有发送记录，不新增绕过审核的发送路径。

上限均可配置为 0，表示关闭该项数量限制。楼层去重独立开关。以上默认值是本期产品选择，不是平台官方安全阈值，也不承诺不会触发平台风控。

草案中的“先占用户额度，再占全局额度”不是完整的原子准入；第二步失败会造成第一步泄漏。本单要求楼层、用户、账号预算在同一事务中判断与登记。

不强制新增 `ReplyGate` 类。优先在现有 Repository 提供少量原子方法，由通知处理和真实发送入口调用。若提取辅助函数能减少重复，可提取，不建立新的平行业务层。

## 3. 必须统一的语义

### 3.1 两类预算

**通知处理预算**按“接受的一次通知处理尝试”计费：通过准入、准备读取上下文时登记一次，后续生成失败、空回复、审核拒绝、模拟运行也不返还。这样不能通过诱导失败无限消耗模型。

这是保守的处理次数上限，不是精确的模型 API 次数或 Token 配额：一次处理中的图片理解、压缩和 Provider 回退仍按现有超时/数量预算执行。上下文读取失败也可能消耗一次处理预算，面板和文档必须说明。

**真实评论额度**按“可能实际产生一条评论的发送尝试”占用：`sending/sent/send_unknown` 均占用；确定未发送的失败释放。待审、模拟和单纯生成不消耗真实发送额度。

不把这两类数字混入 `daily_counters.reply_count`。

### 3.2 身份、账号与日期

- 预算中的 `account_id` 取程序读取的发送账号凭据 UID；不得取通知正文、昵称或工具参数。
- 首次准入将该 UID 持久绑定到事件，重试不得改绑；同时核对通知服务持有的客户端/自身 UID 与当前凭据，阻止旧服务残留通知被新账号认领。`_dispatch`、事件对象、生成完成提交审核时必须传递并核对同一个 expected_account_id。若准入后换号，旧任务停止，不允许 `_dispatch` 重新读取新 UID 后悄悄沿用旧预算发到新账号。不能只依赖事件对象从 message.self_id 读取账号，因为当前 `_dispatch` 会重新取客户端（`adapter.py:349–356`、`event.py:61`）。
- 无可核验发送 UID 的自动通知停止准入并记录凭据原因，不创建空账号预算桶；不影响现有无凭据手动模拟返回 dry_run 的能力。升级前无法可靠归属的旧事件按第 7 节处理，不猜成新账号的通知。
- 同一 UID 登录到多个 `profile_id` 时，共享账号总处理预算、评论发送额度和楼层占位；不同 UID 各自独立。记录保留 `profile_id` 用于追踪。
- 单用户预算按 `(account_id, sender_key, UTC day)` 计算；真实发送者取 `Notification.sender_uid_verified` 对应的 UID。
- UID 缺失统一进入该账号的 `unverified` 预算桶，不能用每条通知都不同的本地身份锚点绕过数量限制，也不能授予主人权限。该桶只用于限额，不表示这些通知属于同一个人。
- 日边界沿用现有 UTC 日期；北京时间每日 08:00 切换。界面时间仍可显示北京时间，必须标明额度重置时刻。
- 跨天审核批准按**实际发送尝试当天**计入真实发送额度；昨日已占的未知发送保留在昨日，不自动变为今日的新尝试。

### 3.3 楼层作用域

- 有 `root_comment_id`：`(account_id, post_id, root_comment_id)`；不同用户在同一楼层继续追问也会被挡。
- 没有根评论的帖子级 @：按 `(account_id, post_id, post_scope)` 限一次。不要用外部通知 ID 生成每次不同的键。
- 兼容解析器现有“缺根评论时用评论 ID 兜底”行为；本期不猜测平台未提供的楼层关系。真实样本无法定位同楼层时，仍由用户/账号预算兜底，并记录此限制。
- 楼层占位覆盖 `mention/reply`；主动浏览沿用原有按帖子过滤，不把一次主动顶层评论当作整帖所有通知楼层都已回复。
- 已发送楼层记录在 `retention.dedup_days` 范围内有效，不承诺无限期；未核实的未知发送保留占位，不因到期自动释放，与现有未知发送清理保护一致。成功记录清理后只能依赖剩余去重和预算。

### 3.4 主人豁免

默认只豁免**单用户处理次数上限**。不豁免楼层去重、账号总处理预算、真实发送上限、现有黑名单、审核、模拟开关和平台冷却。

必须满足 `sender_uid_verified` 且与该档案的非空 `owner_uid` 一致。保持 `PermissionService` 现有黑名单优先级；不得拿 `is_owner` 为理由放开所有闸门。

## 4. 生成前原子准入

### 4.1 建议数据结构

在 `xiaoheihe.db` 新增一张通知准入明细表，例如 `reply_admissions`。最低需要：

| 字段 | 用途 |
|---|---|
| `id`、`incoming_event_id`、`attempt_no` | 关联一次事件处理尝试；事件加尝试号唯一 |
| `profile_id`、`account_id`、`sender_key` | 档案、发送账号、对端预算身份 |
| `day`、`admitted_at` | 预算归属 UTC 日期和登记时间 |
| `post_id`、`scope_key`、`floor_active` | 楼层占位；成功/未知和待审保留，明确结束可释放 |
| `outcome`、`updated_at` | 未执行、执行中、待审、成功、未知、失败、拒绝、模拟等阶段，支持条件领取与恢复 |

使用 `(incoming_event_id, attempt_no)` 唯一约束保证同一处理尝试不重复计费。`attempt_no` 必须表示真正重新执行上下文/生成的次数；不能无条件等同现有 `retry_count`：`schedule_retry` 递增后者，`defer_event` 不递增，而 `dry_run_mark_processed=false` 会 defer 后再次生成（`repository.py:361–426`、`runtime.py:267–283`）。优先复用可满足语义的字段；不满足时在准入记录维护最小的持久尝试号，不改既有网络重试上限的意义。

准入幂等与执行独占分别验证：返回既有准入 ID 不能等同允许再次 build/dispatch。进入 `context_builder.build()` 前以条件更新领取该次执行权，只有领取成功者可继续；重复调用仅返回既有阶段。未开始的同尝试恢复不重复计费；已开始的上下文/生成需要重新执行时，必须先确认旧执行已停止、无审核/发送，再按新尝试计费。阶段不确定时保留占位并停止自动重放，不凭超时释放，也不允许重复恢复免费调用模型。

楼层开启时，为 `floor_active=1` 的 `(account_id, scope_key)` 建条件唯一索引；scope_key 必须同时编码 post_id 和根楼层/帖子级作用域，不能只存 root_comment_id。关闭时该次不占楼层。新增按账号/日期、账号/对端/日期索引。

所有准入行都计入对应日期的处理次数，即使楼层占位后来释放也不退处理预算。无需再建一套可加减的用户日计数表；当前上限和索引下优先查询这张小明细表，避免缓存计数漂移。

### 4.2 单个事务的行为

Repository 新增一个原子准入方法，返回可解释的允许/拒绝结果及准入 ID。事务内依次完成：

1. 校验事件归属、发送账号绑定和当前阶段；已存在同一尝试时返回既有记录及是否取得执行权，不新增预算。先核查已有审核/发送关联，不能仅凭 incoming_events.status 判断可重新生成。
2. 检查楼层是否被其他事件占用；同事件明确重试只能在旧执行已终止、无待审/发送/未知时接续占位。新尝试通过所有预算后，在同一事务将旧行 floor_active 置 0、新行置 1，避免条件唯一索引与“接续自己”冲突；失败回滚整个转移。
3. 主人未豁免时检查单用户预算，再检查账号总预算。
4. 全部通过才插入准入行和楼层占位，任一步失败都不改变前面预算。

必须使用 `Database.transaction()` 的 `BEGIN IMMEDIATE` 和数据库唯一约束；不能“事务外查 `sent`，事务内只加计数”。事务内直接使用该连接，避免再次调用会获取 `_write_lock` 的 `db.execute()` 造成死锁。事务中不做网络请求或模型调用。

建议原因代码与文案：

| 原因代码 | 面板文案 |
|---|---|
| `reply_scope_taken` | 同一楼层已有回复任务或已回复 |
| `reply_user_daily_limit` | 该用户今日通知处理次数已达上限 |
| `reply_account_daily_limit` | 账号今日通知处理次数已达上限 |
| `comment_account_daily_limit` | 账号今日评论发送次数已达上限 |

事件 `error` 写固定中文文案，日志记录稳定原因代码；如关联任务需要按原因查询，可以同步新增小型原因字段，不依赖解析用户文本。

### 4.3 通知链路接入

实际位置为 `NotificationService._handle()`：

```text
事件入库与幂等领取
→ 现有自身消息/缺 UID 自身消息保护
→ 风险评估与人工/自动封禁（第二阶段）
→ PermissionService.decide()
→ 原子通知准入
→ context_builder.build()
→ _dispatch() / CommunityAgent
→ PublishingService.submit_comment()
→ 统一审核或自动批准
```

准入拒绝：`ignored + should_filter=True + 固定 error`，不写假发送记录、不重试、不调用上下文、图片理解、压缩或主模型。事件先入库后判定，不因过滤丢失审计和轮询游标进度。

`enqueue()` 已有权限调用只用于主人优先级；不得在那里产生扣额/加分副作用。`_handle()` 与重试恢复才是本期需要覆盖的正式路径。

终止回调与重试必须结算同一个准入尝试：空回复、上下文/生成失败、`expire_reply` 截止、管理员拒绝，以及现有 `fail_reply` 都要检查执行阶段和审核/发送关联。当前 `mark_event` 为无条件 UPDATE、`fail_reply` 未保护 ignored（`repository.py:336–351`、`runtime.py:618–637`），实施时须用条件更新保护终态；迟到回调不能释放新尝试占位、重置已过滤事件或把已入审核的任务重新排入模型。

## 5. 全部真实评论共用发送闸

### 5.1 复用 outgoing_replies

在已有 `outgoing_replies` 按需增加 `account_id`、可信发送来源、审核关联键等少量字段，不新建平行的发送计数表。

- 稳定发送键优先取统一审核 ID；有事件时同时关联 `incoming_event_id`，并传到 deliver/发送明细；当前该调用只传 event_id，未传 review_id（`publishing.py:208–213`）。无事件的手动评论也必须有稳定键，不能让所有 event_id=None 共用一个键，也不能每次内部重试随机换键。
- 通过原子方法把“检查当前 UTC 日该账号有效发送数”与“写入 `sending` 尝试”放进同一个事务。
- 统计 `sending/sent/send_unknown`；`failed/retry_wait/dry_run` 不计真实发送额度。
- 计数按可信 `attempted_at` 所属日，不按审核创建日、确认日或事件发布时间。
- 同一幂等发送键的重复调用必须先返回/核对已有尝试，不再次登记或再次发请求；Repository 还须返回本次是否新建并取得发送权，只有创建者能发送，不能让两个调用者拿同一 sending 行都发 HTTP。仅既有路径允许且已确认未发送的明确重试，才可原子创建下一发送尝试号；审核 failed/rejected 不自动改回 pending，释放额度不代表获得重发授权。
- `send_unknown → sent` 只是确认原尝试，不增加次数；统计从明细推导，避免确认后再次 `+1`。

默认所有经过插件的真实评论都计入：通知、主动浏览、Dashboard 手动评论、指令/LLM 工具评论、`send_by_session`。发帖/删除不属于本次“评论上限”，仍受已有发布权限、模拟与冷却控制。

### 5.2 审核与真实发送衔接

`PublishingService.approve()`、`RuntimeServices.deliver()` 和 `ReviewQueue` 一起完成以下行为：

1. 模拟批准先按现有规则返回，不占发送额度。
2. 批准前检查凭据 UID、当前预算、策略和风险；等待一天的旧审核也要读取当前配置。
3. 真正发送仍必须在 `deliver()` 中做原子额度检查；审批前的只读检查仅用于用户体验，不能替代原子闸。
4. 单纯额度/新策略拒绝且确定未写入发送尝试时，审核项应保持 `pending` 并显示原因。不能让 `approve()` 的通用异常捕获将它错误变成 `failed/send_unknown`。
5. 若审核已被原子领取才遇到本地策略拒绝，可增加一个最小的“确认尚未开始发送才释放领取”的状态转换。只能处理特定本地拒绝异常，且通过条件更新和发送记录核验；未知网络结果绝不能退回待审。
6. 在等锁、启动服务和原子发送登记等新增 `await` 后，真实请求前重新校验持久绑定 UID、客户端 UID、当前凭据、模拟开关与当前策略；保留目前“领取前不可插入换号”的安全效果。登记后因确定的本地拒绝停止且尚未调用 HTTP 时，条件结算该尝试为确定未发送，释放发送额度再退回待审；无法证明未发送则转未知。取消落在登记返回前后也必须可由持久键恢复，不能留下可再次发送的悬空领取。
7. 真正 HTTP 发送前把尝试持久化为 `sending`；发送后的异常继续沿用现有明确失败/未知分类。

两份 SQLite 库无法靠一边的事务实现跨库原子提交，不要求引入分布式事务。使用稳定事件/审核关联键、幂等状态更新和启动核对解决中断窗口；不得假设两库状态永远同步。

### 5.3 审核全来源与本地拒绝结果契约

- `review_events` 允许多个来源映射同一审核；虽然正常原生 `_delivery` 元数据差异通常会改变 fingerprint，这个多对一关系仍是审核层已支持的契约（`core/review.py:92–100,131–156`）。提交命中既有审核、拒绝、成功、未知、明确失败及启动恢复时，都须枚举该审核的全部可信来源，幂等结算各自事件/准入占位；不能只用 payload._delivery.event_id，也不能为每个来源复制一条真实发送计数。
- 来源解析须按 source 区分 notification/proactive/proactive_candidate；候选 source_id 是 candidate:<id>，不能一律转成事件 ID。由现有候选/事件关系解析，并校验 kind/profile/account 与绑定，保留兼容旧 payload 的核对路径。后续来源绑定到已终态审核时也立即补做结算，不等下次重启；关系无法核实则保留占位并告警。
- 同审核 pending/sending/sent/send_unknown 的全部通知来源保留楼层；rejected 或确定未发送的终止失败释放全部对应通知占位，处理预算均不退。同一来源只能结算其当前关联尝试，重复结算不得改动已接续的新占位。阶段二批准复查须检查全部通知来源；任一被封禁即阻止该审核，不从主动/手动来源推断通知发送者。
- 确认未发送的本地额度/策略拒绝通过现有 JSON 成功封装返回可识别结果：`{status:"pending", policy_blocked:true, reason:"comment_account_daily_limit", message:"账号今日评论发送次数已达上限", review:...}`，review.status 必须仍为 pending；第二阶段沿用此契约并扩展固定 reason。不能仅抛 ValueError/HTTP 400，因为现有面板会将 API 异常当作发送未知。读取策略失败不伪造 policy_blocked；失败时停止发送并走明确错误路径。
- `pages/account/publishing.js::showResult` 与审核操作处理必须展示“未发送，仍待审核”及固定原因，保留稍后重新审批/拒绝能力，包括刷新失败时旧卡片按钮恢复；自动批准遭此拒绝也返回同一结构。普通 pending 仍显示已加入队列；网络丢响应/真正未知仍禁用重复发送。联动 `core/dashboard.py` 响应、`main.py` 工具/指令结果及 `tests/test_dashboard.mjs`，不能只修改 app.js。审核领取回退须比较本次领取标识/状态，避免迟到处理撤销另一审批；本地拦截不得留下本次新增的发送冷却，回滚时不能覆盖其他并发操作的冷却。

## 6. 状态与恢复规则

| 场景 | 通知处理预算 | 楼层占位 | 真实发送额度 |
|---|---|---|---|
| 权限/风控/准入拒绝 | 不新增 | 不新增 | 不新增 |
| 已准入，生成/上下文明确失败 | 已花费，不退 | 明确终止时释放；重试受剩余预算约束 | 不新增 |
| 排队/同尝试恢复 | 不重复计费 | 保留 | 不新增 |
| 明确重新生成的重试 | 新尝试再次计费 | 接续原事件，不能把自己当他人占位 | 到真实发送再判断 |
| 生成完成待审 | 已花费 | 保留，避免待审期间反复生成 | 不新增 |
| 管理员拒绝 | 已花费，不退 | 释放，后续新事件可触发 | 不新增 |
| 模拟批准仍待审 | 已花费 | 随待审保留 | 不新增 |
| 无待审项的终态模拟 | 已花费 | 可释放；dry_run_mark_processed=true 时原事件不重放 | 不新增 |
| 模拟且 dry_run_mark_processed=false，无审核项 | 已花费；下轮重新生成须新尝试计费 | 旧执行结束后接续占位，受剩余预算约束 | 不新增 |
| 确认发送成功 | 已花费 | 保留至去重保留期 | 计一次 |
| 确定未发送失败（含明确 429） | 已花费 | 按既有重试/终止决定保留或释放；审核已 failed 时结算终止，不对同事件重新生成 | 失败尝试不占；仅允许的下一真实尝试重新占 |
| 发出请求后取消/超时/响应不确定 | 已花费 | 保留 | 计一次，禁止自动重发 |

启动恢复必须：

- 在启动轮询、重试恢复和保留清理之前完成已有事件、审核（包括 `review_events` 全来源）、发送明细与占位核对；当前 ensure_started 只恢复主动候选，不代表已有此跨库恢复（`runtime.py:102–112`）。不要靠猜测耗时超限自动释放。
- `sending`/审核遗留 `sending` 维持当前未知处理，额度保守保留；审核遗留 sending 但尚无 outgoing 时也不能自动退回 pending 或释放楼层，告警说明额度明细尚未建立。
- outgoing 已 sent、审核因重启成 send_unknown 时，用同一稳定发送键的确定成功证据幂等补齐审核及全来源事件；保留原 attempted_at，不创建新发送或重新计费。审核已 pending/rejected/failed 而事件未同步，按可信关联补齐，不能让 recover_pending 仅凭 dispatched 将待审任务误判成可重新生成的失败。
- 只有明确无待审、无发送、已终止的占位才能释放；关系无法确认时保留并告警，供管理员处理。
- 不重新执行已经 `dispatched` 且无法确认旧管线结果的任务，保持当前重复分发保护。
- 任务取消/晚到 Agent 回调不能覆盖已完成、已过滤或未知事件状态。

## 9. 验收用例

### 离线必测

- [ ] 不同通知/不同评论同时命中同楼层，只有一条到上下文构建/模型；失败准入不留下部分扣额。
- [ ] 相同楼层不同 UID 仍受一次规则；不同根楼层独立；空根评论和解析器兜底有固定预期。
- [ ] 同一用户上限 5、第 6 次被挡；账号上限 30、多用户并发第 31 次被挡。
- [ ] 相同账号不同档案共用总限额/楼层；不同账号独立；中途换 UID 不转移旧审核或旧额度。
- [ ] 主人仅跳过单用户预算；缺 UID 统一桶、昵称冒充主人无效。
- [ ] 重复入队/恢复同尝试不多扣，明确重新生成的重试扣新一次；失败/拒绝不退生成处理预算。
- [ ] 同事件同尝试并发调用仅一方获得执行权；已开始执行后的恢复不能免费重复 build/模型；新重试在预算不足时不留下失去归属的楼层占位。
- [ ] 拦截事件 `ignored/should_filter/error` 正确，无上下文/图片/压缩/模型调用，无死信和重试风暴。
- [ ] 待审长期占位；拒绝释放；模拟仍待审与终态模拟按各自语义处理。
- [ ] dry_run_mark_processed=false 的延后再次生成计入新尝试；空回复/截止/最终失败释放正确；迟到回调不改 ignored/待审/新尝试；无凭据手动模拟行为保留。
- [ ] 通知、主动、面板、指令/工具和会话发送共享真实发送上限，关闭审核也不能绕过。
- [ ] UTC 跨天前生成、次日批准按实际发送日计费；失败结算不会扣错日期；未知确认不重复计数。
- [ ] 确定失败释放发送额度；未知不释放；异常发生在请求前/请求后有区分。
- [ ] 额度不足时审核保持 pending；并发额度竞争、审批/拒绝竞争和新增 await 后换号不误发。
- [ ] 本地拦截返回 pending+policy_blocked+固定 reason；publishing.js 显示未发送及原因，刷新失败仍可重新审批/拒绝；解封/跨日后审批成功，丢响应/真正未知仍不能重发。
- [ ] 同审核多个可信来源，命中既有 pending/终态审核、拒绝、成功、失败和重启都结算全部来源且幂等；不重复占发送数，不误把 candidate:<id> 当 event_id。
- [ ] 同发送键并发只有创建者发 HTTP；登记后/HTTP 前开模拟、换号、封禁和取消正确结算；本地拒绝不残留本次冷却、不撤销别的领取或冷却。
- [ ] 重启发生在准入后、提交审核前后、领取审核后、HTTP 前后、确认成功与写审核终态之间，均无重复生成/发送或静默额度丢失。
- [ ] 从 v0.7.1 数据库升级，已有待审/成功/未知、去重保留期和清理顺序符合规格。
- [ ] 默认值/schema/校验/API/页面一致，0/负数/bool/大整数和恢复旧配置有覆盖。
